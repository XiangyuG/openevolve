# Task
Propose changes that will improve the program's FITNESS SCORE -- lower execution
time per program run, with the result still provably equivalent to the original.
Propose any change you can justify as preserving the program's observable
behavior (its return value and its final map state for every input).

Most changes -- eliminating dead code or a redundant computation, hoisting a
repeated map lookup or kernel read out of a branch/loop, simplifying control
flow, strength reduction, tightening a loop bound the verifier already proves --
heimdall verifies directly by proving full equivalence, no relaxation. A few
SCHEMA changes need a developer-approved witness before heimdall does a relaxed
check for them:
  - narrow a BPF hash/array map's VALUE struct (fewer bytes) when the real value
    range never needs the current width
  - narrow a hash map's KEY type when the key value provably always fits (e.g. an
    RX queue index that is always < 65536 -> a u16 key)
  - merge two or more maps looked up with the SAME key in the SAME code path into
    one map whose value struct unions the originals'

Changes that skip work on some calls (sampling, rate-limiting, caching that drops
updates) change the final map state and will not verify as equivalent -- do not
propose them. Keep the code verifier-safe (bounded control flow), keep every
SEC() section and the events it attaches, keep the required includes and the
license declaration, and do not stub the program out.

If there is no safe improvement, propose the smallest qualifying change (or none
at all) and say so in the explanation.

## Transformation-witness DSL (the ```witness block)

Two blocks, in this fixed order, both optional and may be empty. Every
statement ends with `;`. Grammar: c2rust_translation/witness_dsl/GRAMMAR.bnf.

    assumption {{
        original.ctx.<field> in [<lo>, <hi>];   // value-range precondition; either side; hex / negative allowed
    }}
    binding {{
        original.<map>[k] = optimized.<map>[k]; // entry-wise correspondence between the two maps; k is a free key variable
    }}

A <path> is a name then any run of `.field`, `[k]` (k a variable), or `[:]`
(every entry of a map). There is no `observation` block: heimdall always
compares every output (return value, every map, every `.data` global) --
the DSL cannot narrow what gets compared, only add premises. These words are
reserved and may NOT be used as names: assumption binding in ignore flag of
original optimized.

## What these blocks mean to the checker (read before writing any assumption/binding)

`assumption` and `binding` are NOT independently verified -- heimdall's solver
takes them as given facts and proves full equivalence using them as premises.
If an assumption or binding is actually false for some real input, the checker
can still report the change equivalent, because the false premise silently
ruled out the counter-example that would have caught it. Only write one if
it's something the real code already guarantees (an existing range check, a
type's natural width, a verifier-enforced bound) -- never write one just
because it would make the proof go through. If you cannot point to why an
assumption is actually true, leave `assumption`/`binding` empty and only
propose the change if it verifies as a plain equivalence-preserving change
without them (see "Choosing the blocks" below).

The one exception: when the DSL narrows a map's value/key width or fuses two
maps, heimdall independently cross-checks the claimed byte widths against the
object files' real BTF metadata before honoring it. Everything else here,
including any `assumption`/`binding` you write directly in the DSL, is
trusted on your word alone -- so it is the one place in this whole proposal
where being wrong has a real cost: a badly justified assumption can turn a
genuinely broken change into one the developer approves believing it was
proven safe.

Choosing the blocks:
  - Narrowing a map VALUE or KEY (fewer bytes): put the range that makes it
    lossless in `assumption` (on the ctx field it derives from) and relate the
    two maps entry-wise in `binding`. Every output is compared regardless, so
    this map (and everything else) still has to check out equal.
  - A plain equivalence-preserving change (hoisting a lookup, dropping a dead
    store, tightening a loop bound, a pure refactor): leave `assumption` and
    `binding` empty -- there is nothing else to write.

## Format

I propose the following changes:
(1) <one-line summary of the change>
    ```witness
    <the transformation-witness DSL program for this change>
    ```
    Example: `<short fragment of the OLD code>` -> `<short fragment of the NEW code>` (in <function/section name>)
    Witness: <2-4 plain-English sentences: why the ```witness above holds for every input>
    Formula (pre-transformation): (assert true)
    Formula (post-transformation): (assert true)
(2) <one-line summary of the change>
    ```witness
    <...>
    ```
    Example: `<...>` -> `<...>`
    Witness: <...>
    Formula (pre-transformation): (assert true)
    Formula (post-transformation): (assert true)

Leave the two "Formula (...): (assert true)" lines exactly as shown UNLESS this
change narrows a width; then instead make each a self-contained SMT-LIB 2 snippet
over shared Int inputs -- pre declares a constant `pre_result` for the OLD value,
post re-declares the same inputs plus a `post_result` for the NEW value -- proven
equal for every input. Only Int/Bool sorts, no bitvector ops (approximate a mask
with `mod`), nothing after the final `)`.

Then add AT MOST ONE of the following tag lines, directly after the
post-transformation formula, and only when it exactly describes this change --
omit all three otherwise. Without one of these tags, a map-value-width or
map-key-width change from the SCHEMA list above is checked with NO relaxation
and will only verify if the two object files are already byte-for-byte equal
on that map, which a real narrowing never is -- so it MUST carry the matching
tag below or it cannot be approved into the relaxed check. (Map fusion has no
tag yet; a proposed map merge is always checked as a plain, non-relaxed change.)

  Map value width change: <map_name>: <old_bytes> -> <new_bytes>
      -- this change shrank that map's VALUE struct.

  Map key width change: <map_name>: <old_bytes> -> <new_bytes> key <ctx_field> < <bound>
      -- this change shrank that hash map's KEY type. The "key <ctx_field> <
      <bound>" clause is REQUIRED: <ctx_field> is the BPF context field the key
      is derived from (e.g. rx_queue_index, cpu, common_pid) and <bound> is the
      exclusive limit it never reaches (e.g. 65536 for a narrow to 2 bytes).
      Your formulas MUST also prove it: assert `(< <ctx_field> <bound>)` on the
      shared input in the pre-transformation formula and model the post one as
      truncation (e.g. `(assert (= post_result (mod k 65536)))`).

  Variable width change: <var_name>: <old_bits> -> <new_bits>
      -- this change narrowed a scalar VARIABLE from a proven range invariant.
      Assert the range on the shared input in the pre-transformation formula
      and model the post one as truncation (e.g.
      `(assert (= post_result (mod v 16)))` for an unsigned narrow to 4 bits).

Each "Example" line must quote a real, short fragment (a line or part of a line) of
the actual before/after code you are proposing, wrapped in single backticks -- not a
triple-backtick block -- so a reviewer can see exactly where the change would happen
without you having written the whole diff. This is REQUIRED, not optional: even if

constant/macro edit, you must still quote the actual old and new text in backticks.
Never leave this line (or its Old:/New: equivalent) with no code after the label.
